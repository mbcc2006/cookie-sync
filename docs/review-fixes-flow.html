CookieSync 修复流程图

2026-10-27 · 对应 review 的 #1、#3–#10，以及性能、可维护性、站点、Redis 几项（#2 按决定不修）。虚线框是需要俊然拍板或单独同意的节点。

1. relay 请求入口：兜底不崩（#1）

HTTP handler 和 upgrade handler 外面各包一层兜底。解析 URL 或路径解码失败时返回 400，其他异常记日志并返回 500，进程不会退出。请求体读到一半断开时直接结束这次请求。

flowchart TD A[收到请求] --> B{new URL / decodeURIComponent
能解析?} B -- 否 --> C[400 bad_request] B -- 是 --> D[限流] D --> E[路由 handler] E -- 抛异常 --> F[console.error + 500 internal] E -- 正常 --> G[响应] U[WS upgrade] --> UB{URL 能解析且鉴权通过?} UB -- 否 --> UD[socket.destroy] UB -- 是 --> UE[handleUpgrade
maxPayload 64KB + 30 秒 ping]

2. 存储后端选择（Redis 主存储）

relay 启动时按环境变量选后端。两个后端实现同一组异步接口，handler 不关心底层是哪个。redis 包只在设置了 URL 时才动态加载，CLI 用户不用加载它。

flowchart TD S[createRelay 启动] --> R{COOKIE_SYNC_REDIS_URL
是否设置?} R -- 是 --> RD[动态 import redis
连接 Redis] RD --> RS[RedisStore] R -- 否 --> JS[JsonStore
内存 Map + 1 秒合并写
SIGTERM/SIGINT 前强制刷盘] RS --> H[handlers 统一 await store.*] JS --> H

Redis key 设计（前缀 cs:，值是 JSON 字符串）：

数据key过期策略
配对cs:pair:{code}不设 TTL。还有设备、消息、导入引用它时不能删，由清扫任务判断
设备cs:device:{id}，索引 cs:pair:{code}:devices（set）不过期
快照消息cs:msg:{id}，最新指针 cs:latest:{deviceId}:{domain}，索引 cs:pair:{code}:msgs（zset）EXPIRE 7 天；索引里指向已过期 key 的条目在读取时顺手清掉
Console 导入cs:import:{id}，索引 cs:pair:{code}:importsEXPIRE 5 分钟
访问请求cs:access:{id}，到期队列 cs:access:exp（zset）由清扫任务处理，到期时要写一条「expired」审计，所以不用 EXPIRE
审计cs:audit:{deviceId}（list，LPUSH + LTRIM 500）保留 90 天，读取和清扫时过滤
推送订阅cs:pair:{code}:push（hash，以 endpoint 去重）随配对一起删除

一次性语义必须是原子的，否则并发时同一个访问授权可能被消费两次。所有「读一条记录、判断、再改写」的操作，都走一个 Lua 写成的 CAS 函数（GET 出来比较旧值，相同才 SET，并保留 TTL），冲突就重试：

flowchart LR A[update key, fn] --> B[GET 旧值] B --> C[fn 旧值 → 新值
不满足条件则返回 null] C -- null --> X[按业务返回 403/409] C -- 新值 --> D[Lua: 当前值 == 旧值 ?
SET 新值 KEEPTTL] D -- 成功 --> OK[完成] D -- 冲突 --> B

用到 CAS 的场景：访问请求 consume（设置 usedAt）、approve/deny 决定、Console 导入上传信封（一次性 token）、更新设备资料和策略。

3. 导出取数：relay 没有新快照时回退到本地（#5、#6）

cookies / playwright 跟 browse / yt-dlp 改成一样的处理。relay 返回 no_message 时，改用本地上一次保存的快照，并在 stderr 提示这份快照的同步时间。注意：这种情况下扩展的审计记录只有「请求、批准」，没有「已读取」，因为数据并没有从 relay 读出来。

flowchart TD A[cookies / playwright domain] --> B[申请访问授权
提示信息走 stderr] B --> C[GET /v1/messages] C -- 200 --> D[解密 → 写本地快照 → DELETE 消息] C -- 404 code=no_message --> E{本地有快照?} E -- 有 --> F[stderr 提示: 使用本地快照
同步于 syncedAt] E -- 没有 --> G[报错 + 提示去扩展里允许该网站] D --> H[输出] F --> H H --> I{有 --out?} I -- 有 --> J[写文件，提示走 stdout] I -- 没有 --> K[stdout 只输出数据]

4. 撤销通知链路（#8）

CLI 撤销配对后，relay 主动通知并断开扩展。扩展只在 401 响应里带有明确的 code（device_revoked 或 unknown_device）时才清除凭据，避免 relay 临时故障导致所有用户被解除配对。

flowchart TD A[CLI revoke] --> B[DELETE /v1/pairs/:code] B --> C[删除配对、设备、消息、导入、访问请求、审计、推送订阅] C --> D[向该配对下的设备 WS 推送 revoked 并关闭] C --> E[关闭该配对的 CLI WS] D --> F[扩展收到 revoked] G[扩展上传/轮询收到 401] --> H{body.code 是
device_revoked / unknown_device?} H -- 是 --> F H -- 否 --> I[保留凭据，下次重试] F --> J[清除 deviceId/uploadToken/publicKey
弹出通知「已被 CLI 撤销」
弹窗回到未配对状态]

待拍板 / 需单独同意的事项

  • 本地测 Redis：WSL 里如果没有 redis-server，需要俊然用 ! wsl sudo apt install -y redis-server 装一下（要输入 sudo 密码）。
  • 字体：下载完先报告文件数和体积，俊然确认后再上传 R2（预计 1000 个以上文件、可能超过 100MB）。
  • 服务器四步（侦察、装 Redis、部署加迁移、切换），每一步动手前都会先说明连哪台、跑什么命令，等您同意。
  • 站点 deploy:site、npm 发版、扩展上架都不在这次范围内，除非您另外吩咐。
